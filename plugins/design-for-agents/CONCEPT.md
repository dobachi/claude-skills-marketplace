# design-for-agents — 基本コンセプト

> 人間向けに書かれたデザイン知を、**AIが迷わず引ける形**に組み直した参照体。
> 価値は知識の新しさではなく、**AIが誤らない引き方ができること**にある。

status: draft / 2026-08-29

---

## 1. 解こうとしている問題

AIエージェントは資料・UI・図を日常的に生成するが、その出来を**自分で見られない**。
画像を読ませることは可能だが、コストが高く、生成ループの中で毎回回すには重い。
ここから2つの失敗が生まれる。

**(a) 検証ループが切れている。**
人間は「作る→見る→直す」で品質を上げる。AIはこの「見る」が欠けるため、
生成はできても検算ができない。結果、それらしいが破綻した出力が通る。

**(b) 空欄にした判断は、統計的中央値で埋まる。**
指示しなかった選択は、学習データの最頻値に落ちる。それが
「紫グラデーション＋Inter＋3枚の特徴カード＋グラスモーフィズム」に代表される
AI slop である。Tailwind の `indigo-500` 既定が全モデルに吸われた、という水準の話。
**原則を並べたドキュメントでは (b) は直らない。決め打ちの値が要る。**

したがって本リポジトリが提供すべきものは「デザイン原則集」ではない。
**判断が空欄にならないよう決め打ちされ、適用条件と完了条件が明示された、
ユースケース単位の手順書**である。

## 2. 設計原理 — AIを制御するための工夫

以下は装飾ではなく、**すべてのファイルが満たすべき構造要件**である。
このリポジトリの価値はここに集約される。

| # | 工夫 | 何を防ぐか |
|---|---|---|
| 1 | 入口は1つ。`INDEX.md` のルーティング表だけを常時読む | 全文読み込みでトークンを溶かす／読み飛ばす |
| 2 | プレイブックの `when:` は判定可能な条件。曖昧なら聞く、まで明記 | 誤ったプレイブックを選ぶ |
| 3 | 決め打ち値を書く。「検討せよ」「適切に」を禁止 | 未指定の判断が統計的中央値＝slopに落ちる |
| 4 | 権威の階層 MUST / SHOULD / HOUSE を全ルールに付す | 規範・ブランド・ユーザ指定が衝突したとき解決が揺れる |
| 5 | 1ファイル1判断。安定IDで参照する | 引用・差分更新・トレースができない |
| 6 | 各手順に完了条件 `done_when` を、**後から検出器に落とせる書式**で書く | 「やった」で終わり、検算されない |
| 7 | アンチパターンは抽象的な戒めでなく具体名で禁止 | 「品位を保て」の類は行動を変えない |
| 8 | 各ルールに出典と「適用しない条件」 | 機械的に適用して文脈を外す |
| 9 | 語彙を固定する（`glossary.md`） | 同じ概念を別語で呼び、指示が通らない |

### 6 についての補足（最重要）

検出器（自動チェック）の実装は v0.2 以降に回す。ただし **`done_when` は最初から
検出器互換の書式で書く**。こうすることで、後から検出器を足す作業が
「書き直し」ではなく「実装の追加」になる。

```yaml
done_when:
  - id: no-free-textbox
    statement: "全スライドがレイアウトのプレースホルダに書かれている"
    check: manual          # v0.2 で automated に昇格
    check_later: "audit_pptx.py 相当"
  - id: title-is-assertion
    statement: "各スライドのタイトルが主張文である（体言止めのトピック名でない）"
    check: manual
    floor: "スライドが3枚以上あること"
```

`floor`（下限）は、**削除によって条件を満たすことを禁じる**ための項目である。
「コントラスト違反ゼロ」は本文を全部消せば達成できてしまう。
検証条件には必ず、消して満たせなくする下限を添える。

## 3. 権威の階層と衝突解決

AIは渡された指示を同格に扱いがちで、ユーザ指定のブランド色とアクセシビリティ規範の
どちらを優先するかで揺れる。階層を明示して、衝突解決を決定的にする。

| tier | 中身 | 上書き |
|---|---|---|
| **MUST** | 外部の規範（WCAG、可読性の下限など）。逸脱は欠陥 | 不可 |
| **SHOULD** | 業界の広い合意（グリッド、行長、データインク比など） | 理由を書けば可 |
| **HOUSE** | 迷いを消すための本リポジトリの決め打ち | ユーザ指定・ブランドがあれば即上書き |

**解決順**: MUST > ユーザ／組織の明示指定 > SHOULD > HOUSE。
HOUSE の存在理由は「決めないと中央値に落ちるから」であり、
上書きされること自体は失敗ではない。

## 4. 知識の単位

知識を4種類に分ける。それぞれ役割が違い、混ぜない。

| 種別 | 置き場 | 役割 |
|---|---|---|
| playbook | `playbooks/` | ユースケース単位の手順書。**AIの入口はここだけ** |
| rule | `rules/` | 1つの判断だけを書いた原子ファイル。playbook から ID で引かれる |
| token | `tokens/` | 決め打ちの値。W3C DTCG 形式（独自形式を作らない） |
| antipattern | `antipatterns/` | 具体名で禁止された事項 |

**各ファイルの書式（frontmatter の全フィールド、ID 体系、`done_when` の文法）は
[`docs/format-spec.md`](skills/design-for-agents/docs/format-spec.md) が正である。** ここには再掲しない。

書式のうち、設計上の判断として押さえるべきは次の3点である。

- **`tier` と `source.kind` は1対1に対応する。** 権威と出典を別々に判断しない。
  出典が出せないものは `HOUSE` であり、外部規範のふりをさせない
- **`done_when` の条件は6つの述語（`exists` / `absent` / `count` / `member` /
  `ratio` / `equal`）のいずれかに還元できなければならない。** できないものは
  完了条件ではなく `needs_human` である
- **検証手段の無いルールは追加しない。** rule は `verified_by` で
  自分を検証する `done_when` を指す

## 5. AI から見た読み方

```
INDEX.md（ルーティング表のみ）
  └─ 該当する playbook を1本だけ読む
       └─ 必要な rule を id で引く（全件読まない）
            └─ tokens/ から決め打ち値を取る
生成 → done_when を1つずつ確認 → 満たさないものを直す
     → 「見ないと判断できない項目」を明示してユーザに返す
```

最後の一行が本リポジトリの誠実さである。**美しさ・ブランド適合・写真選定は
テキストでは判定できない。** それを「できたことにしない」ことまで規定する。

## 6. 範囲外（やらないこと）

- ファイル生成そのもの（`.pptx` を書くのは `pptx-build`）
- ブランド固有のトークン定義（各プロジェクトの DTCG ファイルに委ねる）
- 「良いデザインとは何か」の一般論・美学の議論
- 画像／視覚による品質判定（検出できない項目として人に返す）

## 7. 既存資産との関係

本リポジトリを**上流**、既存スキルを**消費者**とする。

| 既存 | 関係 |
|---|---|
| `pptx-design` | references/ の中身を本リポジトリの playbooks / rules / tokens に抽出・再構造化し、スキル側は薄くして ID 参照に寄せる |
| `pptx-build` | 生成の実装。本リポジトリは仕様と完了条件を供給する |
| `document-figures` | 図の生成。図に関する rule を本リポジトリから参照 |
| `claude-skills-marketplace` | 独立repoとして作り、後からプラグインとして登録 |

二重メンテを避けることが最優先。同じ内容を2か所に書かない。

## 8. ロードマップ

### v0.1 — PowerPoint、参照できる状態まで

- `INDEX.md` のルーティング表
- playbook 8本。**直交する4軸**に分ける。ジャンル・要素・制約を1枚の
  リストに並べると `when:` が排他にならず、要件2（誤ったプレイブックを選ばない）
  を満たせないため。
  - モード（既存資料のとき先に読む、1本）: `pptx-mode-refactor`
  - デッキのジャンル（必ず1つだけ、3本）: `pptx-deck-decision` /
    `pptx-deck-explain` / `pptx-deck-pitch`
  - 要素（置く分だけ、3本）: `pptx-element-table` / `pptx-element-chart` /
    `pptx-element-diagram`
  - 制約（該当する分だけ、1本）: `pptx-constraint-template`
- rule 20〜30枚（`pptx-design` からの抽出＋出典の補完）
- `tokens/`（色4枠・型スケール1本・グリッド・密度予算）を DTCG 形式で
- `antipatterns/`（PowerPoint 版の slop カタログ）
- `glossary.md`
- 薄いルータスキル 1本

### v0.2 — 検出器

`done_when` の `check: manual` を `automated` に昇格。stdlib のみで実装。

### v0.3 以降 — 媒体の拡張

web/HTML、chart、diagram、document。共通ルールを媒体非依存層へ引き上げる。

## 9. 公開方針

private で作成し、内容を確認してから public に切り替える（履歴に未レビュー内容を
残さないため）。

**コードは Apache-2.0**（`LICENSE`）。著作権表示はテンプレートのまま残さない。

`pptx-design` からの派生は README の1節で示す。NOTICE ファイルは置かない
（両者とも同一の著作者であり、Apache-2.0 第4条の告知義務が生じる関係ではない）。
