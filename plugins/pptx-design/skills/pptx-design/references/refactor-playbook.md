# Refactor Playbook — fixing a deck that already exists

Most decks arrive already built: inherited from a predecessor, assembled by
several people, generated by a tool, or written by you in a hurry. Refactoring
one is a different job from designing a new one — the content is given, the
argument is half-formed, and the temptation is to restyle instead of re-argue.

This file is the diagnosis and the decision. The mechanics (extract → rebuild)
live in `pptx-build`'s `references/refactor-mode.md`.

## The rule

**Refactoring preserves the argument and changes the form.** Anything that
changes what the deck claims is not a refactor — it is a rewrite, and it needs
the author's agreement before you touch it.

Two failure modes bracket the work:

- **Restyling** — new colors and fonts over a deck that still does not argue
  anything. The deck looks better and persuades no one.
- **Silent rewriting** — "improving" claims while cleaning up. The author
  presents a case they did not make and cannot defend under questioning.

When a slide is wrong rather than ugly, say so and leave the claim standing;
list it as a finding for the author to settle.

## Diagnostic pass

Read the deck five times, in this order. Stop after each pass and write findings
down — a mixed pass turns into restyling.

1. **Titles only.** List every title in order and read it as a document. Does it
   argue one case? Where does the thread break? Titles that are topic labels
   ("Q3 実績") cannot carry an argument at all — mark each one.
2. **One message per slide.** Mark every slide carrying two claims, and every
   slide carrying none.
3. **Evidence.** Every number: is its source on the slide? Every chart: does it
   support the title's claim, or merely sit near it?
4. **Structure vs. decoration.** Apply the information test to every diagram,
   box, arrow, and SmartArt block. Deleting the shapes — what is lost?
5. **Form.** Only now: type sizes, alignment, color count, bands, density,
   contrast, alt text. Against `clean-design-system.md`.

## Triage

Fix in this order. Later items are wasted effort on a deck that fails earlier ones.

| Order | Finding | Fix |
|---|---|---|
| 1 | No governing thought — the deck does not argue one case | Restructure the spine before touching slides; get the author's agreement |
| 2 | Topic titles | Rewrite as action titles that state the takeaway |
| 3 | Slides with two messages, or none | Split, merge, or delete |
| 4 | Claims without evidence or source | Add the source, or downgrade the claim |
| 5 | Decorative diagrams, SmartArt theater, filler shapes | Delete, or redraw so they encode the structure |
| 6 | Wrong chart for the question; 3-D, exploded pie | Re-pick per `data-visualization.md` |
| 7 | Density over budget, shrunken type | Split the slide; never shrink |
| 8 | Ornament: bands, gradients, shadows, extra colors | Delete; apply `clean-design-system.md` |
| 9 | Accessibility: contrast, alt text, reading order, unique titles | Fix before delivery |

## Patch or rebuild

| Situation | Do |
|---|---|
| A few slides need edits; the master and layouts are sound | **Patch in PowerPoint.** Rebuilding would throw away a working master |
| The deck is a corporate template's, and only the content is bad | **Patch**, or extract and refill the same template (`--template`) |
| Content sits in free textboxes on blank slides; nothing follows the master | **Rebuild.** Patching preserves the disease |
| The argument itself is being restructured | **Rebuild** — reordering, splitting and merging is text work, not slide work |
| More than about a third of the slides need structural change | **Rebuild** |
| The original file is a template you must return in place (tracked changes, review cycle) | **Patch**, and note the design debt |

Rebuild means: extract the content to a spec, fix the argument as text, and
render a new file — `pptx-build`'s `extract_deck.py` → edit → `build_deck.py`.
Text is where an argument is cheap to change; slides are where it is expensive.

## Refactor without changing the argument

- Keep the author's wording unless the finding is that the wording is the problem.
  Tightening a title into a takeaway is in scope; changing what it claims is not.
- Keep every number, unit, caveat, and source. If a number appears twice with
  different values, report the contradiction — do not pick one.
- Keep speaker notes. They carry the half of the argument that is not on the slide.
- Deleting a slide is a content decision. Propose it; do not do it silently.
- When you split a slide, the two new titles must both be true and must not
  overlap — a split that duplicates the claim is not a split.

## Reporting the result

Hand back three things, not just a file:

1. **What changed structurally** — slides split, merged, reordered, deleted, with
   the reason in one line each.
2. **What could not be carried over** — diagrams that had to be redrawn, content
   that did not survive extraction, anything the spec cannot express.
3. **What you did not touch and why** — findings that are the author's to settle:
   contradictions, unsupported claims, slides whose message you could not
   determine.

A refactor the author cannot audit is a rewrite they have to trust blindly.
