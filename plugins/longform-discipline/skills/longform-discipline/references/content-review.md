# Content Review — 意味とコンテキストの点検

`drift_scan.py` は表層しか見ない。表記も文体も数値も揃った長文が、**主旨を述べていない・章がつながっていない・
読者が知らない前提で書かれている**ことは普通に起きる。ここはその点検手順である。

規律7（「人には番号付きの具体リストを渡せ」）は、**このリストを作る手順が無ければ空手形**になる。この
ファイルがその手順で、出力はスキャナと同じ形式に揃える — 機械の指摘と人手の指摘が1つのリストで読める。

## 原則

- **スキャナが拾えるものは拾わせる。** 語の不在、未検証の主張、定義前の用語、無出典の断定は
  `--spine` 付きの `drift_scan.py` が出す。ここで人がやるのは**その先**だけ。
- **AIに採点させない。** 「この章は主旨を述べていますか？ 10点満点で」は禁止（規律6）。聞くのは
  **答えが具体物になる質問**だけ — 「この章が主旨を述べている文を、原文のまま1つ引用せよ。無ければ『無し』」。
  引用は検証できる。点数は検証できない。
- **章ごとに、新しい文脈で。** 全文を積んで一度に点検しない（規律1・軸1）。点検も執筆と同じ制約下にある。
- **見つからなかったことも書く。** 「§5は確認したが指摘なし」と書く。沈黙は未点検と区別がつかない。

## 手順A — 章ごとの内容点検

各章について、**スパイン + その章だけ**を読み込んで、次の5問に答える。答えは講評ではなく**原文の引用か「無し」**。

| # | 問い | 答えの形 | 該当する failure |
|---|---|---|---|
| A1 | この章の主旨（スパインの `Claim it must land`）を述べている文を、原文のまま1つ引用せよ | 引用 / 無し | 主旨の不達成 |
| A2 | この章で、根拠を示さずに事実として述べている文をすべて引用せよ | 引用の列挙 / 無し | 無出典の主張 |
| A3 | この章が、読者（スパインの `Audience`）の知らない語・前提を説明なしに使っている箇所を引用せよ | 引用の列挙 / 無し | 読者前提との齟齬 |
| A4 | この章の内容で、前の章の記述と食い違うものを引用せよ（両方） | 引用の対 / 無し | 章間の矛盾 |
| A5 | この章で、主旨に寄与していない段落を引用せよ | 引用 / 無し | 目的に寄与しない節 |

A4は前章の要約ではなく**前章の原文**と突き合わせること。要約どうしの比較は、矛盾が要約の段階で消える。

## 手順B — 継ぎ目の点検（隣接章の対ごと）

規律4のシーム作業に、内容の観点を足す。§N と §N+1 を並べて:

| # | 問い | 答えの形 |
|---|---|---|
| B1 | §N の結論と §N+1 の冒頭の前提の間に、書かれていない飛躍があるか。あれば両方を引用せよ | 引用の対 / 無し |
| B2 | §N+1 が §N の内容を言い直している箇所を引用せよ（`cross-section-dup` が拾えなかった**言い換え**） | 引用 / 無し |
| B3 | §N で定義した語を §N+1 が別の意味で使っている箇所を引用せよ | 引用 / 無し |

B2は現状の逐語重複検出の穴を人が埋めている。ここが埋まらないなら埋め込みの導入を検討する（BACKLOG）。

## 手順C — 全体の点検（章が出揃ってから）

| # | 問い | 答えの形 |
|---|---|---|
| C1 | スパインの `Desired impact` を、この文書は達成しているか。達成の根拠となる章と文を引用せよ | 引用 / 無し |
| C2 | スパインの `Outline` にあって本文に無い主旨、本文にあってスパインに無い主張を列挙せよ | 列挙 / 無し |
| C3 | 予備知識のない読者が最初に詰まる箇所はどこか。原文を引用せよ | 引用 |

C3は `doc-coauthoring` の Reader Testing と重なる。両方走っているならそちらに寄せてよい。

## 手順D — 意図と成果物の突き合わせ

訂正に限らず、**何かを書くたび**に走らせる。スキャナは完了条件が「書かれているか」と「対象に語が
あるか」までしか見ない。満たされたかは人が見る。

| # | 問い | 答えの形 |
|---|---|---|
| D1 | この意図の完了条件を満たしている文を、原文のまま引用せよ | 引用 / 無し |
| D2 | 完了条件と関係のない変更を、この作業でしたか。したなら引用せよ | 引用 / 無し |
| D3 | いま作っているものを一行で言うと何か。台帳の「意図」列と同じか | 一行 / 「同じ」 |

**D3が本体である。** 台帳に書いた意図と、いま口で言う意図が違っていたら、その時点でずれている。
気づいた時点で選ぶ — 元の意図に戻るか、台帳を**注記つきで**更新するか。黙って続けるのだけが駄目。

長い作業では D3 を**節の切れ目ごと**に。往復5回に1度で十分だが、思い出したときには遅い。

## レビューリストの作り方

手順A〜Dの答えと `drift_scan.py --json` の findings を、**1つの番号付きリスト**にまとめる。形式はスキャナに揃える:

```
[check] 章 L行番号 — 指摘

 1. [claim-coverage]  第3章 評価 L11 — 主旨「遅延と可用性の両立が実証された」の語が本文に無い
 2. [unverified-claim] 第3章 評価    — K-2「可用性は99.9%を満たす」出典なし
 3. [A2-unsourced]    第4章 展望 L17 — 「標準化はすべての障壁を取り除く」根拠の記述なし
 4. [B1-gap]          第2章→第3章    — §2は構成で終わり、§3は評価条件を既知として始まる
 5. [A3-audience]     第2章 構成 L8  — 「エッジケース」を定義せずに使用（Audience: 実装担当者）
 6. [C2-orphan]       第4章 展望     — スパインの主旨「標準化が普及の前提」に対応する記述なし
 7. [D3-shift]        I-1 第1章      — 台帳は「前提の明示」だが、直近3往復は語尾を直している
 …
 点検済みで指摘なし: §1, §5
```

**渡し方の規則:**

- **並べ替えない。** 重要度でソートすると、下位が読まれない。章順に並べる。
- **1項目1行。** 説明を足したくなったら、それは指摘ではなく提案なので別に分ける。
- **「レビューお願いします」を付けない。** リストが依頼そのもの。
- **点検済みで指摘なしの章を明記する。** 沈黙と未点検が区別できる唯一の方法。
- **AIの判断だと分かるように書く。** `[A2-unsourced]` のように手順IDを残す。機械の指摘
  （`[claim-coverage]`）と人・AIの判断（`[A2-…]`）は、信頼度が違う。

## いつ走らせるか

ループのステップ7（`SCAN` の直後、`HANDOFF` の前）。ただし手順Dは**作業のたび**に、手順Aは**章を書き終えた直後**に、その章だけ
やっておくのが安い。全部書いてからまとめてやると、直しが章をまたいで波及する。

## この手順で扱わないもの

- **事実そのものの正誤** → `verify-content` / `fact-checker` / `evidence-check`
- **論証の妥当性・反論の欠如** → `doc-review`（ジャンル別ルーブリックを持っている）
- **削るべきか** → `essence-distiller`
- **AIっぽさ** → `ai-tell-reducer` / `humanize-prose`

ここが扱うのは「**スパインで宣言したことを本文が実際にやっているか**」だけである。それ以外は上に渡す。
